## Major

### M1 — Python version inconsistency between `pyproject.toml` and `start.sh`

- **File:** `pyproject.toml:4`, `backend/start.sh:6`
- **Found:** `pyproject.toml` declares `requires-python = ">=3.14"` (and `dependencies = []`, which is also misleading). `backend/start.sh` pins `uv venv --python 3.11`. `uv` warns on every fresh venv: "The requested interpreter resolved to Python 3.11.15, which is incompatible with the project's Python requirement: `>=3.14`". Tests run cleanly on 3.11.
- **Suggested fix:** Pick the version the code actually targets (3.11 based on tests) and align `pyproject.toml`. Alternatively delete the root `pyproject.toml` if it isn't used.

### M2 — App startup hard-requires Postgres

- **File:** `backend/app/lifespan.py:12`
- **Found:** `Base.metadata.create_all(bind=engine)` runs synchronously in the lifespan. If the DB is unreachable, the lifespan raises `sqlalchemy.exc.OperationalError` and uvicorn exits with code 3. Consequences: `/health/db` can never report "db down" (the app isn't running to respond), `/openapi.json` is unreachable for CI / tooling without spinning up a real DB, and any DB outage is upgraded to a full app outage on restart.
- **Suggested fix:** Move DDL to an explicit migration step (Alembic or a `python -m app.bootstrap_schema` script). Let the app start when the DB is down; the existing `/health/db` handler already deals with that case correctly.

### M3 — `create_all` instead of migrations for schema management

- **File:** `backend/app/lifespan.py:12`
- **Found:** `create_all` creates missing tables but never alters existing ones. Schema drift between model code and the DB is silent — a renamed column, new constraint, or modified index is not applied. The `.env.example` and code comments already acknowledge that interests / summaries / transports / scores DDL is owned outside the app (HSE coursework), making `create_all` mostly dead but live for any new model added in the future.
- **Suggested fix:** Adopt Alembic and remove `create_all`, or document explicitly that the DDL is owned outside the app and have the app refuse to start if expected tables are missing.

### M4 — `JWT_SECRET` defaults to a publicly-known placeholder

- **File:** `backend/app/core/config.py:21`
- **Found:** `jwt_secret: str = "dev-only-change-me"`. If the env var is unset in production, the app starts silently with a key anyone reading this codebase knows. That's a path to forging session JWTs for arbitrary user ids.
- **Suggested fix:** Drop the default (force env), or add `@model_validator(mode='after')` that refuses to start if `jwt_secret == "dev-only-change-me"` and `cookie_secure is True` (i.e. fail only on production-shaped configs). See also m26 about `.env.example`.

### M5 — `PUT /score` backend exists but no frontend caller (companion to C1)

- **File:** `backend/app/api/score.py:14`, `backend/tests/api/test_score_api.py`
- **Found:** The backend route is implemented and well-tested (6 cases including cross-user 404). No frontend call exists in `frontend/src/shared/api/calls/`. C1 is the user-visible consequence; this entry exists so the backend side is tracked in the per-area appendix.
- **Suggested fix:** See C1 — wire the call from Home.tsx.

### M6 — `conftest.py` uses `setdefault` for `DATABASE_URL`, fragile when shell has it set

- **File:** `backend/tests/conftest.py:9`
- **Found:** `os.environ.setdefault("DATABASE_URL", "sqlite:///:memory:")` only sets if missing. Anyone who exports `DATABASE_URL` (common after `source backend/.env`) silently runs pytest against real Postgres — which has both a correctness risk (tests mutate real data) and a confusion risk (tests fail differently depending on shell state).
- **Suggested fix:** Force-assign `os.environ["DATABASE_URL"] = "sqlite:///:memory:"` at the top of conftest, before any app import.

### M7 — `TransportRepository` has no direct tests

- **File:** `backend/app/repositories/transport_repository.py`, `backend/tests/`
- **Found:** `Transport` uses Postgres JSONB which SQLite cannot model, so `tests/api/test_transports_api.py` substitutes a `_StubTransportService` at the dependency boundary. Coverage of `ensure_active_for_user` (SELECT-then-INSERT pattern, see m2), `get_active_for_user` (`deleted_at IS NULL` filter), and JSONB read/write paths is effectively zero. The 22 transport API tests pass on stubs that do not exercise SQL.
- **Suggested fix:** Add `tests/integration/test_transport_repository.py` gated on a running Postgres (use testcontainers-postgres in CI), or refactor `Transport.data` to a JSON-string column and exercise via SQLite.

### M8 — `OAuthProvider` doesn't validate `VITE_APP_CLIENT_ID`

- **File:** `frontend/src/features/Auth/OAuthProvider.tsx:3`
- **Found:** `const clientId = import.meta.env.VITE_APP_CLIENT_ID;` is passed straight to `<GoogleOAuthProvider clientId={clientId}>`. The frontend `.env.example` ships `VITE_APP_CLIENT_ID=` (empty). When unset, GoogleOAuthProvider receives `undefined` and Sign-In silently breaks (console error only, no user-facing message).
- **Suggested fix:** `if (!clientId) throw new Error("VITE_APP_CLIENT_ID is required");` at module load so dev/CI catches it before deploy. Pair with a friendly error UI for production.

### M9 — `tsconfig.app.json` does not enable `"strict"`

- **File:** `frontend/tsconfig.app.json`
- **Found:** `strict: true` is not set. `strictNullChecks`, `noImplicitAny`, `strictFunctionTypes` are all off. Some hygiene options (`noUnusedLocals`, `noUnusedParameters`, `verbatimModuleSyntax`) are on, but the most valuable null/undefined catches are missing. Symptoms appear in the code (defensive `String(user?.username ?? 'user')` casts).
- **Suggested fix:** Add `"strict": true` and fix the resulting errors (estimated 1-3 dozen in this codebase). Land in a dedicated PR with no behaviour changes.

### M10 — `postLogout` doesn't check `response.ok`

- **File:** `frontend/src/shared/api/calls/auth.ts:18`
- **Found:** `await apiFetch('/auth/logout', { method: 'POST' });` swallows any non-2xx. AuthProvider's `logout()` (`features/Auth/AuthProvider.tsx:68-74`) then clears the local user via the `finally` block regardless. If the request fails (5xx, network blip), the HttpOnly session cookie may still be live on the server while the UI shows the user logged out.
- **Suggested fix:** Check `response.ok` and either retry once or surface a "Logout may not have completed — close all tabs" warning.

### M11 — `getSessionUser` / `getInterest` / `getTransport` conflate "no data" with "server error"

- **File:** `frontend/src/shared/api/calls/auth.ts:10`, `interests.ts:8`, `transports.ts:9`
- **Found:** All three return `null` on **any** non-2xx response. A 500 looks identical to "user not logged in" / "no data". `AuthProvider.tsx:37-52` then treats `null` from `getSessionUser` as "not logged in" and routes the user to the Login page. A single transient backend error logs everyone out.
- **Suggested fix:** Split error states. For `getSessionUser`, only treat 401 as "not logged in"; for others, surface the actual error so the page can show "Try again" instead of pretending the data is just empty.

### M12 — `guest.spec.ts` has no snapshot baseline in the repo

- **File:** `e2e/tests/guest.spec.ts:22`
- **Found:** `toHaveScreenshot('unauthenticated-landing.png')` with no `*-snapshots/` directory committed. First run is guaranteed to fail without `--update-snapshots`. There is effectively no visual baseline today, and no CI to regenerate one.
- **Suggested fix:** After C3 is fixed, regenerate the baseline (`npm run test:update-snapshots`) and commit `tests/guest.spec.ts-snapshots/`. Add a CI job that fails on diff.

### M13 — E2E coverage gap on core user flows

- **File:** `e2e/tests/`
- **Found:** The suite has one guest test (visual) and one authenticated smoke test. No coverage for: saving / clearing the Telegram bot token (`PATCH /transports`), the hello-capture polling flow (`POST /transports/telegram-capture-hello`), the score/feedback UI (any path), redirect to Login on 401 from `getSessionUser`, pagination (PREV/NEXT) on the summary list.

### M14 — `backend/README.md` cannot get a new contributor to a running server

- **File:** `backend/README.md`
- **Found:** Four lines of useful content. Doesn't mention `.env` setup or how to get `GOOGLE_CLIENT_ID` / `JWT_SECRET` / `E2E_BOOTSTRAP_SECRET`. Instructs the user to run `start.sh`, which deletes `.venv` on every invocation and then blocks running uvicorn (see m1).
- **Suggested fix:** Replace with a real Quickstart: copy `.env.example` to `.env` and fill marked values, `bash db.sh`, `uv venv && uv pip install -r requirements-dev.txt`, `.venv/bin/python -m uvicorn app.main:app --reload --port 8000`, `pytest`. Note Python version requirement.

### M15 — `frontend/README.md` doesn't mention `.env` or `VITE_APP_CLIENT_ID`

- **File:** `frontend/README.md`
- **Found:** Three lines. No mention of copying `.env.example` to `.env` or filling `VITE_APP_CLIENT_ID`. A first-time contributor lands on a login page that silently breaks (see M8).
- **Suggested fix:** Add a Quickstart: copy `.env.example` to `.env`, fill `VITE_APP_CLIENT_ID`, `npm install && npm run dev`. Link to the backend Quickstart.

### M16 — No top-level orchestration (Makefile / CONTRIBUTING / dev script)

- **File:** (repo root)
- **Found:** Standing up the full stack requires reading three READMEs (currently two are wrong or near-empty), starting four processes manually (Docker postgres, backend, frontend, eventually Playwright), and knowing which `.env` lives where. There is no `Makefile`, `justfile`, `taskfile`, or `scripts/` entrypoint.
- **Suggested fix:** Add `Makefile` (or `scripts/dev.sh`) with `make dev` (postgres + backend + frontend), `make test` (backend pytest + e2e), `make stop`. Also add a one-screen root `README.md` explaining what the project is and pointing at `make dev`.

## Minor

### m1 — `backend/start.sh` blocks after venv setup

- **File:** `backend/start.sh:8`
- **Found:** Script ends with `.venv/bin/python -m uvicorn ...` which blocks. Not usable for "just set up the venv" automation (CI, the audit I just ran).
- **Suggested fix:** Split into `setup.sh` (venv + deps) and `start.sh` (uvicorn), or accept `--no-run`.

### m2 — `TransportRepository.ensure_active_for_user` is SELECT-then-INSERT

- **File:** `backend/app/repositories/transport_repository.py:19`
- **Found:** Two concurrent requests for the same user could both observe no row and both INSERT. Low impact in practice (UI is single-user-at-a-time) but trivial to make worse.
- **Suggested fix:** Use SAVEPOINT + ON CONFLICT DO NOTHING, or add a partial unique index on `(user_id) WHERE deleted_at IS NULL` and recover from `IntegrityError` like `UserRepository.get_or_create` already does.

### m3 — `UserRepository.list_all_ids` is unbounded

- **File:** `backend/app/repositories/user_repository.py:19`
- **Found:** Materializes every user id into memory; called by the nightly summary job. Coursework scale is fine; production scale isn't.
- **Suggested fix:** Iterate via server-side cursor or chunked SELECT in the job path.

### m4 — Placeholder email written to `user.email` is indistinguishable from a real address

- **File:** `backend/app/repositories/user_repository.py:8, 30`
- **Found:** When Google doesn't return an email, `_placeholder_email(google_id)` writes `"<google_id>@google-subject.local"` into the unique `email` column. Downstream code reading `user.email` cannot tell it's a placeholder.
- **Suggested fix:** Make `User.email` nullable (with a partial unique index `WHERE email IS NOT NULL`), or add an `email_is_real: bool` column.

### m5 — `generate_summary` (and a few siblings) return untyped `dict`

- **File:** `backend/app/api/summary.py:32`, `backend/app/api/tasks.py:11`, `backend/app/api/auth.py:111`
- **Found:** These return `dict[str, bool | int]` / `dict[str, int]` / `dict[str, bool]` instead of a typed Pydantic `response_model`. OpenAPI shows `additionalProperties: true`, so the frontend gets no compile-time shape guarantee.
- **Suggested fix:** Define `SummaryGenerateOut`, `BulkRunOut`, `LogoutOut` and use `response_model=`.

### m6 — `PostgresSummaryService` silently rewrites the requested page number

- **File:** `backend/app/services/summary_service.py:71`
- **Found:** When the client requests page > total_pages, the response sets `page = total_pages` without flagging that the page was clamped. Behaviour is documented by a unit test (`test_clamps_page_above_total`), so it's intent — just surprising for callers.
- **Suggested fix:** Either 422 on page > total_pages, or add a `clamped_from: int | None` field to the response.

### m7 — `patch_profile` accepts empty-string `name`

- **File:** `backend/app/api/users.py:27`, `backend/app/schemas/user.py:11`
- **Found:** `UserProfilePatch.name: str | None = None`. An empty string `""` overwrites `user.name` to empty.
- **Suggested fix:** `Field(min_length=1)` on `name` and `picture`, or treat empty-string as no-op explicitly.

### m8 — `ScoreOut.value` aliases the ORM `score` column without explanation

- **File:** `backend/app/schemas/score.py:18`
- **Found:** Response field `value: bool | None` is sourced from `Score.score` via `validation_alias="score"`. Readers see two names for the same thing with no comment about why.
- **Suggested fix:** Either rename the ORM attribute to `value` (HSE coursework DDL may or may not allow this) or drop the alias and expose `score` directly with a brief docstring noting the SQL column name.

### m9 — Naive UTC datetime convention is implicit

- **File:** `backend/app/core/time.py`, all `app/models/*.py`
- **Found:** Every `DateTime` column is `timezone=False`. The codebase writes via `naive_utc_now()` and only re-attaches UTC awareness in `summary_service._as_utc`. Anywhere else that compares timestamps directly is fine today but a footgun for new features.
- **Suggested fix:** Switch to `DateTime(timezone=True)` and have `naive_utc_now` return aware UTC, OR document the convention with a docstring on `time.py:4`.

### m10 — CORS `allow_methods=["*"]` + `allow_credentials=True` relies on origin list never containing `*`

- **File:** `backend/app/main.py:14`

## Severity rubric

- **Critical** — wrong/broken at runtime: 500s where 4xx is expected, data corruption risk, auth bypass, dev environment won't start, pytest already broken on a clean checkout, user-facing features that silently do nothing.
- **Major** — missing HTTP error handling on user-facing endpoints, real bugs in non-critical paths, security footguns gated only by env hygiene, meaningful test gaps for core flows (login, summary fetch, transports config, score upsert), missing setup docs that block onboarding.
- **Minor** — readability, naming, dead code, misleading comments, brittle tests, doc cleanup, defensive code that no longer earns its weight.

## Method

**Stage 1** verified the project starts on a clean checkout. Docker socket access was unavailable, so the FastAPI server could not be started (lifespan requires Postgres) — see M2. The OpenAPI schema was extracted by importing `app.openapi()` directly. Pytest ran 119/119 green.

**Stage 2** captured the OpenAPI schema and diffed every route against `frontend/src/shared/api/calls/`. Two server endpoints have no frontend caller (`PUT /score`, `PATCH /user`); both turned into real findings (C1/M5, m21). No client→nonexistent-server calls were found. No schema-shape mismatches between Pydantic responses and TS types.

**Stage 3** read every backend module (api → services → repositories → models → schemas → core/scheduler/lifespan), every frontend module (pages → features → shared/api → shared/ui), every existing pytest test, every Playwright spec, and every doc/env file. Findings logged as they appeared, then organized by severity.

**Stage 4** (this report) consolidated, assigned stable IDs, and built the appendix.

No code outside `docs/` was modified during this audit.
